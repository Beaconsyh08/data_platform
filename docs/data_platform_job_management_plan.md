# 数据平台任务管理实施计划

本文是待实现方案，不代表下述功能已经上线。核对基线：2026-09-08 当前工作区。

## 1. 结论与第一版范围

任务信息可以存入现有控制面数据库。继续使用当前 MySQL / SQLAlchemy 存储和 Agent 执行方式，
这一轮不引入 Ray，也不另建一套任务调度平台。

第一版目标：任务重启后仍可查询，执行历史完整；支持符合条件的任务重试、安全取消、删除和恢复记录。
先打通远程任务，再接入本地任务。暂停、断点续跑和自动重试作为后续能力，不能仅靠修改状态字段实现。

| 用户操作 | 计划语义 | 边界 |
| --- | --- | --- |
| 重试 | 原任务下创建新的执行批次，保留旧日志和结果 | 第一版只手动重试；参数或输入变化则新建任务 |
| 取消排队 | 尚未领取时直接取消 | 与领取操作竞争时必须事务判定 |
| 中断运行 | 发出取消请求，在安全边界停止并确认 | 不能把页面显示为取消当成进程已经停止 |
| 删除记录 | 已结束任务软删除，可恢复 | 不删除数据集、输出文件、版本或审计记录 |
| 暂停 / 继续 | 保存有效检查点，再从已完成工作继续 | 后续逐算子开放，不等于重试 |

## 2. 当前已经有什么、还缺什么

当前代码已经实现：

- `control_plane.py` 的 `dp_jobs` 保存远程任务类型、参数、状态、租约、结果、错误和时间。
- `dp_job_events` 保存任务事件；Agent 可以领取任务、续租、上报进度和完成结果。
- `ControlPlaneStore` 接受数据库连接地址，可连接 MySQL，也可使用 SQLite。
- 源数据修改已经有权限、备份及部分本地完成标记机制，需要保留。

当前尚未实现：

- 取消、重试、删除和恢复的完整 API / Agent / UI 闭环。
- 独立执行批次、旧执行结果隔离、普遍适用的完成结果补报。
- Flask 本地任务统一持久化；目前部分任务仍在 `viewer.py` 的 `jobs_registry` 内存字典中。
- 通用检查点和暂停恢复。`cancelled` 出现在状态集合中，不意味着执行端已有取消能力。

需要先修正的可靠性问题：

1. `claim_job()` 会重新领取租约过期的运行任务，续租只校验节点，没有执行批次校验。
2. Agent 丢失租约后当前代码仍允许计算继续；数据库租约不能阻止旧进程继续写磁盘。
3. 完成接口在最终状态校验之前会注册位置、移动缓存等；只让数据库完成操作幂等还不够。
4. 计算完成但网络补报失败，当前通用路径不能保证恢复后只补报、不重算。
5. 数据库初始化目前使用 `create_all()`，新增字段需要显式迁移，不能依赖它升级旧表。

## 3. 存储设计：数据库存记录，节点存大文件

| 位置 | 保存内容 | 本轮处理 |
| --- | --- | --- |
| `dp_jobs` | 任务定义、目标数据、当前状态、进度摘要、当前执行批次、删除标记 | 扩展现有表 |
| `dp_job_attempts` | 每次执行的节点实例、租约、起止时间、状态、错误、结果及临时输出位置 | 新增 |
| `dp_job_events` | 带执行批次的进度、日志和状态事件 | 扩展并提供分页 |
| Agent 工作目录 | 完成结果待补报记录、取消确认、检查点清单及诊断文件 | 原子写入，成功同步后按保留策略清理 |
| 数据节点 / 缓存目录 | Parquet、视频、模型产物、完整大日志和分片文件 | 数据库只记录引用、大小、摘要和必要统计 |

数据库是任务查询的权威来源；节点本地记录用于断网补报和恢复，不是另一套用户任务数据库。
节点任务状态目录放在原始数据根目录之外，不能把新日志或检查点写入 raw / standard 数据集。

建议最小字段增量：

- `dp_jobs`：`current_attempt_id`、`revision`、`progress`、`phase`、`cancel_requested_at`、
  `deleted_at`、`deleted_by`，以及可校验的输入身份 / 参数摘要和固定的最终输出位置。
- `dp_job_attempts`：`attempt_id`、`job_id`、递增的 `attempt_no`、`worker_instance_id`、
  执行凭据、租约期限、状态、时间、结果、错误和 `staging_root`。
- `dp_job_events`：增加 `attempt_id` 和事件序号，对同一批次的同一事件去重。

任务定义创建后不原地改参数。执行批次变化不改变逻辑任务身份；worker 数等执行配置不进入
逻辑数据版本摘要。输入优先引用不可变版本；没有版本时记录并在执行 / 重试前校验内容指纹。

重试时，列表显示最新批次状态，详情保留所有历史批次。保留现有 JSON 字段，新增字段按兼容方式返回。
节点或位置注销不应级联清掉历史任务：需要调整现有级联外键策略，并保留必要的目标快照。

## 4. 执行模型与状态规则

保留现有 `queued / running / done / error / cancelled`，增加 `cancel_requested` 和 `interrupted`。
提交产物期间仍为 `running`，通过 `phase=finalizing` 表明正在提交，避免扩大主状态集合。

| 场景 | 状态变化与处理 |
| --- | --- |
| 正常执行 | `queued -> running -> done / error` |
| 排队取消 | `queued -> cancelled`，不得再被领取 |
| 运行取消 | `running -> cancel_requested -> cancelled`，最后一步必须有执行端停止确认 |
| 心跳超时 / 执行端丢失 | 转为 `interrupted`，展示执行状态待核实；不立即重新派发 |
| 手动重试 | 停止情况和产物已核实的 `error / cancelled / interrupted -> queued`，领取时创建新批次 |
| 已完成再次执行 | 新建任务，不覆盖成功执行的历史 |

`interrupted` 不等于机器上进程一定已退出。没有停止或隔离证明时，禁止重试和删除。
`done` 必须意味着校验、产物提交、平台登记及所需缓存刷新已完成，而不只是计算子进程退出。

### 4.1 先隔离执行批次，再开放重试

- 领取时事务性创建执行批次，一个任务只能有一个有效批次。
- 每次 Agent 启动有独立实例 ID，不能把相同 `node_id` 当作相同进程。
- 心跳、事件、上传和完成请求均携带批次 ID 与执行凭据；服务端拒绝已失效批次的写入。
- 每个批次使用独立临时目录；最终输出路径在任务接受时确定，重试不再生成另一个随机输出路径。
- 节点对规范化后的数据 / 输出路径做互斥，覆盖相同源数据的写入及同一输出的提交。
  第一版宁可串行，也不允许两个任务并发修改同一数据。互斥必须覆盖实际子进程的生命周期。
- 心跳失联时停止派发新工作；租约失效后不得发布产物。恢复后先核实进程、互斥锁和本地完成记录。
- 第一版任务固定在数据所在节点，不自动跨节点故障转移。共享文件系统的多节点写入不在本版范围内。

服务端批次校验只隔离 API 写入，不能撤销磁盘写入。节点互斥、独立临时输出和受控提交必须同时存在。

### 4.2 取消必须由执行端确认

Agent 改为“父进程监督任务，子进程执行算子”。父进程负责心跳、控制请求、日志补报和退出确认。
不能尝试强制杀掉 Flask Python 工作线程。

- 控制面记录取消意图，通过任务心跳响应交付给 Agent；重复请求返回一致结果。
- 处理器在文件、分片或阶段边界检查取消信号，不再提交新工作，等待当前不可分割步骤结束。
- 进程池应改为有界提交，并取消尚未开始的工作；只在进度回调里检查无法停止已全部提交的 futures。
- 第一版默认合作式取消。未能停止则继续显示“取消中”，并展示当前阶段，不伪造 `cancelled`。
- 最终提交是不可取消的短临界区；取消和提交的竞争由事务决定，进入提交后取消请求返回 409。
- 后续如开放强制终止，仅对确认使用隔离临时输出的任务开放，终止整组进程并回收 FFmpeg 等子进程。
  强制终止后的残留文件必须隔离和校验，不能注册为成功数据集。
- 源数据原地修改仍是受限管理员能力，不开放通用强杀和自动重试；只在算子实现可恢复安全边界后开放取消。

### 4.3 完成结果必须可补报、可重复确认

- Agent 将计算结果、批次、摘要及提交阶段原子写入本地待补报记录，再请求服务端确认。
- 断网时缓冲进度 / 结果并重发；遥测请求失败不应直接使数据变换失败。
- 服务端先验证批次与状态，再进入提交；重复完成请求不能重复移动缓存、登记版本或失效 Viewer。
- 数据库事务与文件移动不能视为一个原子事务。记录提交阶段和确定性产物身份，允许崩溃后检查并补齐。
- 本地已提交但远端未确认时优先做结果核对和补报，不把它直接当作重新计算任务。
- 沿用当前 Lifecycle 的 staging、校验、原子提交和幂等登记约束，不合并或替换其版本数据库。

## 5. API、权限和页面

保留现有提交接口，增加以下控制接口：

| 接口 | 行为 |
| --- | --- |
| `POST /api/control/jobs/<id>/cancel` | 取消排队任务或登记运行取消请求 |
| `POST /api/control/jobs/<id>/retry` | 校验状态、输入、权限及停止证明，排入新的执行批次 |
| `DELETE /api/control/jobs/<id>` | 软删除已结束且没有待处理提交的记录 |
| `POST /api/control/jobs/<id>/restore` | 恢复软删除记录 |
| `GET /api/control/jobs/<id>/attempts` | 查询执行历史 |
| `GET /api/control/jobs/<id>/events` | 按批次和游标分页查询事件 |

- 控制操作携带预期 `revision` / 幂等请求标识；防止重复点击、过期页面误操作和领取 / 取消竞争。
- viewer 只读；建议 operator 管理自己提交的普通任务，admin 管理全部任务。
  重试重新校验当前权限、允许目录和算子能力；原地修改仍需管理员及现有确认 / reason / legacy 开关。
- 当前任务是否支持取消 / 重试，由服务端返回 `available_actions` 和不可操作原因；前端不自行放宽权限。
- Runs 列表及控制面任务页共同适配新状态，显示当前阶段、执行次数、节点、耗时、错误和操作按钮。
- 删除确认明确说明“只删除任务记录展示，不删除数据”；提供已删除筛选及恢复入口。
- 数据集删除、临时文件清理、日志过期清理分别处理，本版不让删除任务触发这些操作。
- 用户控制操作接入现有操作审计，执行日志继续使用任务事件，不另建一套审计系统；敏感参数必须脱敏。

## 6. 本地任务接入：明确分批，而非宣称已经统一

第一批完成远程任务闭环，第二批把 Flask 本地任务也纳入持久化查询：

- 增加执行来源标识；本地任务允许没有远程 node / location 引用，保存其稳定数据目标和可序列化任务定义。
- `RouteContext.update_job / finish_job / fail_job` 接入持久化，但还需清点 `viewer.py` 中直接修改字典的路径。
- `jobs_registry` 保留为现有页面 / 运行时兼容缓存，数据库作为记录来源；保留 `/api/jobs` 等旧接口字段。
- 旧线程任务重启后应显示中断，不能恢复成虚假的运行中；仅补持久化不会自动获得取消 / 重试能力。
- 先迁移 `viewer.prepare` 和已有远程预处理对应的本地任务，优先复用同机 Agent 执行路径。
- 其他本地任务逐一补齐序列化输入、安全停止和重试契约；未迁移的类型明确禁用相关按钮。
- Lifecycle 物化等领域任务关联已有领域 run / 幂等键，不另起任务绕过其审批、租约和提交流程。

现有集中部署继续使用控制面 MySQL。未配置控制面数据库的单机模式保持兼容；是否启用持久化 SQLite
通过显式配置决定，不能静默创建新数据库或改变旧部署行为。

## 7. 后续检查点：借鉴 Data-Juicer，但按机器人数据格式实现

参考 Data-Juicer 的[分区与检查点设计](https://datajuicer.github.io/data-juicer/zh_CN/main/docs/PartitionAndCheckpoint_ZH.html)：
借鉴“保存已完成工作、恢复前验证输入与配置”的机制，无需先接入 Ray。

- 检查点单位由算子决定：可能是文件、Parquet shard、视频分片或完整阶段，不能统一按 episode 切分。
  LeRobot v3 的同一个 shard 可能包含多个 episode，必须避免恢复时覆盖其他 episode 的结果。
- 检查点记录输入版本 / 指纹、逻辑参数摘要、算子实现版本、已完成单元、产物摘要和聚合统计。
- 恢复时逐项校验；文件缺失、损坏或输入变化不能直接跳过。最终仍执行全量元数据 / 索引 / 时间戳一致性校验。
- 当前失败清理逻辑会删除部分临时输出；实现恢复前需调整保留策略，区分可恢复产物和损坏残留。
- 先选择非破坏性、天然按 shard 独立执行的操作试点，再扩展复杂转换和物化；不承诺所有任务通用续跑。

Data-Juicer 的[处理追踪](https://datajuicer.github.io/data-juicer/zh_CN/main/docs/Tracing_ZH.html)
也可用于展示处理前后样例，但它不替代我们已有的操作审计和完整 episode lineage。

## 8. 实施顺序与验收

| 阶段 | 主要改动位置 | 可验收结果 |
| --- | --- | --- |
| A：执行可靠性基础 | `control_plane.py`、`agent.py`、控制面 routes、数据库迁移 | 批次隔离、路径互斥、完成补报；旧执行不能覆盖新执行 |
| B：远程任务控制 | 同上，以及 Runs / 控制面模板 | 手动重试、安全取消、软删除恢复，全链路权限和审计 |
| C：本地任务接入 | `routes/context.py`、`viewer.py`、具体任务入口 | 本地记录持久化；已迁移类型复用控制能力，其他类型明确受限 |
| D：按算子恢复 | `precompute/` 对应算子与 Agent | 试点任务从有效检查点续跑，再考虑有次数上限的自动重试 |

数据库升级采用版本化、可重复执行的显式迁移，覆盖现有表增量、索引和外键。
第一版推荐维护窗口：暂停领取、等待现有任务结束、备份数据库、迁移并升级控制面和 Agent 后再恢复领取。
Agent 上报协议 / 能力版本；未升级 Agent 不展示新控制能力，也不领取要求新执行协议的任务。
MySQL 与 SQLite 分别验证事务竞争，不能假设 SQLite 具有 MySQL 的行锁行为。

重点测试覆盖：

1. 原有任务和旧 API 兼容；控制面重启后任务 / 日志仍可查询；旧库迁移可重复执行。
2. 两个 Agent 同时领取、取消与领取竞争、双击重试；只能产生一个有效执行批次。
3. 旧批次晚到的心跳、事件、上传和完成请求被拒绝，且不产生文件 / 缓存副作用。
4. 计算完成后断网、上传后崩溃、缓存移动后数据库失败；恢复后核对 / 补报而非盲目重算。
5. 排队取消、运行取消、提交阶段取消，以及进程池 / FFmpeg 退出；状态与实际进程一致。
6. 租约过期但旧进程仍活着时不能开启冲突写入；未确认停止的任务不能重试或删除。
7. 重试保留旧执行历史；参数或输入变化拒绝复用；已存在输出不被静默覆盖。
8. 软删除 / 恢复的权限、幂等与审计；数据集和发布版本完全不受影响。
9. 小型 v2.1 / v3.0 fixture 验证源数据不变、共享 shard 保留、元数据与统计一致、Viewer 刷新。
10. 未迁移本地任务和旧 Agent 不显示不支持的按钮；全部状态过滤与轮询逻辑兼容。

实现时先扩展 `test_control_plane.py`、`test_data_platform_agent.py` 和 `test_console_layout.py`；
涉及算子或本地任务后再补对应预处理、路由和 Lifecycle 回归。这里只规定验收项，不宣称测试已通过。

第一优先级不是添加按钮，而是让重试、停止确认和提交具备可靠语义。完成 A、B 后可先交付远程任务管理；
完成 C 才能按已迁移类型宣称本地和远程任务统一管理，D 则单独标注支持断点续跑的算子清单。
